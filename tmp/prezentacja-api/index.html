Narzędzie, które da się uruchomić tylko wtedy, gdy cudzy serwer ma dobry dzień, nie jest narzędziem produkcyjnym.
02 · Technika

REST, JSON, login i hasło

Nie klucz API w nagłówku — zwykły HTTP Basic Auth. To ma jedną konsekwencję, o której trzeba pamiętać.

# kolekcja placówek — całe śląskie, strona po stronie
GET https://api.rspo.gov.pl/api/placowki/?wojewodztwo_nazwa=ŚLĄSKIE&page=1&pageSize=100
Accept: application/json
Authorization: Basic <login:hasło>

# słowniki do list wyboru (11 sztuk)
/api/typ/   /api/status_publiczno_prawny/   /api/kategoria_ucznia/   /api/etap_edukacyjny/
/api/specyfika_szkoly/   /api/zwiazanie_organizacyjne/   /api/gminy_rodzaje/
/api/wojewodztwa/   /api/powiaty/   /api/gminy/   /api/miejscowosci/

Co warto wiedzieć

  • Paginacja page + pageSize, domyślnie 100 na stronę
  • Odpowiedź to goła tablica JSON — nie ma pola z liczbą wszystkich wyników, więc stronicujemy do pierwszej niepełnej strony
  • Śląskie = 6 116 placówek → 62 zapytania przy 100/stronę, 7 przy 1000
Uwaga bezpieczeństwa. W specyfikacji serwer podany jest jako http://api.rspo.gov.pl — bez S. Basic Auth po czystym HTTP to wysyłanie hasła otwartym tekstem przy każdym zapytaniu. W naszym kodzie adres wpisujemy na sztywno z https://, a login i hasło idą z os.environ — nigdy do repozytorium.
03 · Filtry

18 parametrów — i dwa, których nie ma

Czym zawężamy zapytanie

Terytorialnie: województwo, powiat, gmina, miejscowość — każde po nazwie albo po kodzie TERYT. Tożsamościowo: RSPO, NIP, REGON. Merytorycznie: typ_podmiotu_id, status_publiczno_prawny_id, kategoria_ucznia_id, etap_edukacji_id, zlikwidowana, podmiot_prowadzacy_id / _regon.

Filtr po kodzie TERYT gminy to dokładnie to, na czym stoją nasze rejony. Rejon = lista obszarów (powiat|gmina); poszerzenie rejonu o gminę może się przełożyć jeden do jednego na parametr zapytania. Zero tłumaczenia nazw, zero literówek w „Zabrze” kontra „ZABRZE”.
Czego wśród filtrów nie ma — i co to znaczy:
  • Nie ma „zmienione od daty”. Każde odświeżenie = pobranie całości i porównanie po naszej stronie. Dobra wiadomość: magazyn.py robi dokładnie to od pierwszego dnia — nowe / zmienione / zniknięte plus dziennik zmian pole po polu. API nie wymusza tu ani jednej zmiany.
  • Nie ma szukania po fragmencie nazwy. RSPO, NIP i REGON to „full number”. Rozpoznawanie nazw potocznych („MSP 1”, „Piasek”, „EduHub”) zostaje po naszej stronie — API tu nie pomoże.

Trzy kolumny, które API gubi

Wyjątek od naszej zasady „rejestr nadpisuje swoje pola”. Import z API musi te trzy kolumny pominąć, a nie wyzerować. Inaczej pierwsze odświeżenie z API skasowałoby dane, które mamy poprawne z pliku — i nikt by tego nie zauważył, bo w dzienniku zmian wyglądałoby to jak „rejestr usunął faks”.

07 · Nasza aplikacja

Co trzeba dopisać: jeden plik

Rdzeń rspo_app nie wie i nie musi wiedzieć, skąd przyszły wiersze.

# dziś
plik.py    CSV/XLSX  → lista słowników → magazyn.wgraj() → baza
# po dostępie do API
api.py     JSON      → lista słowników → magazyn.wgraj() → baza
           ^ ta sama lista, ten sam magazyn, ta sama baza

Bez zmian

  • db.py — numer RSPO kluczem głównym
  • magazyn.py — nowe / zmienione / zniknięte, dziennik zmian, bezpiecznik ubytku
  • rejony.py — rejony po TERYT, gmina bije powiat
  • zapytania.py, eksport.py, wykaz do aplikacji leadów

Do dopisania — ok. 1 dzień

  • api.py: stronicowanie, spłaszczenie obiektów i tablic do naszych 34 kolumn, lat/lon
  • login i hasło z os.environ (RSPO_API_LOGIN, RSPO_API_HASLO)
  • przycisk „Odśwież z rejestru” z datą ostatniego odświeżenia — nie cron: automat na serwerze umiera po cichu i nikt nie zauważy przez miesiąc
  • trzy kolumny pomijane przy imporcie z API (slajd 05)
08 · Wniosek

Stan na dziś: wniosek nie został wysłany

W naszych dokumentach (12_RSPO.md, 11_PLAN_v5.md, analiza z 09.08) jest tylko zadanie „wysłać, zegar 14 dni” i lista tego, co ma zawierać. Treści maila nigdzie nie było.

Czego wymaga CIE (§2.3 + wzór PDF)

  • dane identyfikacyjne podmiotu: nazwa, adres, NIP/REGON
  • osoba kontaktowa: imię, nazwisko, mail, telefon
  • osoba odpowiedzialna technicznie za integrację
  • opis planowanego wykorzystania
  • zakres uprawnień — u nas: tylko odczyt
  • aplikacja/system i rodzaj pobieranych danych
  • przewidywana liczba zapytań miesięcznie
  • trzy oświadczenia + podpis

Co już przygotowane gotowe

  • Pełny szkic maila — tmp/wniosek-mail-szkic.md
  • Oficjalny wzór Wniosek.pdf pobrany do tmp/zrodla/
  • Liczba zapytań policzona: ~100–200 na odświeżenie, deklarujemy do 2 000/mies.
  • Opis wykorzystania napisany szeroko (baza + kontakt + rejonizacja + geolokalizacja), bo §3.4 zabrania używania API „do celów niezgodnych z wnioskiem” — wąski opis oznaczałby drugi wniosek przy mapie
Brakuje tylko: adresu, NIP i REGON spółki oraz decyzji, kto podpisuje wzór. Po uzupełnieniu — mail wychodzi tego samego dnia.
